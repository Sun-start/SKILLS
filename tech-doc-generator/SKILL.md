# Tech Doc Generator

为 Java 后端模块生成完整的技术设计文档。

## 核心原则

1. **遇到不确定的地方，必须停下来问，不能假设。** 这是最重要的原则。
2. 文档语言固定为**中文**。
3. 输出文件命名格式：`{模块名}_技术设计文档.md`
4. 技术栈：Java + Spring Boot + MyBatis/MyBatis-Plus，**严格 DDD 四层架构**（见下方分层说明）。
5. 章节结构根据模块类型**动态生成**，不套固定模板，但须完整覆盖该模块的关键设计面。

---

## Java 后端技术栈全景与选型建议

生成文档时，必须根据模块的具体需求主动判断是否需要引入以下技术，并在文档的「技术选型」章节中给出推荐理由。**不是每个模块都要用所有技术**，按需推荐，不推荐的不写。

### 数据存储层

| 技术 | 适用场景 | 不适用场景 |
|---|---|---|
| **MySQL** | 所有业务数据的持久化，唯一数据库选型，不引入其他数据库 | — |
| **Redis** | 缓存热点数据、Session/Token 存储、分布式锁、计数器、排行榜、限流 | 需要持久化的核心业务数据 |

> ⚠️ 注意：本项目数据库**只使用 MySQL**，不引入 Elasticsearch、MongoDB、MinIO 等其他存储。文件存储如有需要，另行与用户确认方案，不默认推荐。

### 消息队列层

| 技术 | 适用场景 | 选型建议 |
|---|---|---|
| **RocketMQ** | 金融级可靠消息、事务消息、顺序消息、国内主流 | 电商/支付/订单类业务首选 |
| **Kafka** | 高吞吐日志流、数据管道、实时计算 | 日志采集、大数据场景首选 |
| **RabbitMQ** | 灵活路由、延迟队列、中小规模异步解耦 | 通知/邮件/短信异步发送场景常用 |

**需要消息队列的典型场景：**
- 操作耗时（发邮件、发短信、生成报表）→ 异步化
- 跨模块解耦（下单 → 扣库存 → 发通知）
- 流量削峰（秒杀、批量导入）
- 事务消息（本地事务 + 消息发送需要一致性）

### 缓存策略

**Redis 使用场景决策树：**
```
接口响应时间是否敏感？
├── 是 → 数据变更频率高吗？
│        ├── 低（文章详情、配置项）→ 推荐 Cache-Aside，TTL 按业务定
│        └── 高（库存、计数）→ 推荐 Write-Through 或直接操作 Redis
└── 否 → 不需要缓存，直接查 MySQL
```

**缓存相关必须考虑的问题（出现缓存设计时须在文档中说明）：**
- 缓存穿透：查不存在的数据 → 缓存空值 或 布隆过滤器
- 缓存击穿：热点 key 过期 → 互斥锁重建 或 逻辑过期
- 缓存雪崩：大量 key 同时过期 → TTL 加随机抖动

### 分布式能力

| 技术 | 适用场景 |
|---|---|
| **Redis 分布式锁**（Redisson） | 防重复提交、并发扣减、定时任务防重跑 |
| **Spring Cloud / Nacos** | 微服务注册发现、配置中心（仅微服务架构需要） |
| **Seata** | 跨服务分布式事务（谨慎使用，性能代价大） |
| **XXL-JOB / Quartz** | 定时任务调度、分布式任务协调 |

### 接入层 & 其他

| 技术 | 适用场景 |
|---|---|
| **Spring Security + JWT** | 认证鉴权、无状态 Token |
| **Spring Security + Sa-Token** | 更轻量的国产鉴权框架，适合单体或轻量级项目 |
| **Swagger / SpringDoc** | API 文档自动生成 |
| **Lombok** | 减少样板代码（getter/setter/builder） |
| **MapStruct** | DTO ↔ Domain ↔ DO 对象转换，替代手写 Assembler |

### 技术选型提问规范

在需求收集阶段，如果以下信息未明确，**必须提问**：

| 不确定项 | 提问示例 |
|---|---|
| 是否有缓存需求 | "这个模块的数据读多写少吗？是否需要引入 Redis 缓存？" |
| 是否需要异步解耦 | "发送通知/邮件这类操作，是否要用消息队列异步处理，还是同步调用？" |
| 消息队列品牌 | "项目里已经有消息队列中间件了吗？用的是哪个？" |
| 分布式锁需求 | "这个操作有并发冲突风险吗？是否需要分布式锁？" |

## 工作流程

### 第一步：需求收集与澄清

用户描述需求后，快速识别以下信息是否已知，**未知的必须提问**：

**必须明确的核心信息（缺一不可）：**
- 模块名称（用于文件命名）
- 模块的核心业务职责是什么（一句话描述）
- 主要对外提供哪些接口/能力（给谁用，怎么用）
- 是否有关联的已有模块/表（外键、依赖关系）

**根据模块类型追加询问（见下方分类）**

提问原则：
- 每次提问不超过 3 个问题，分批次问，不要一次列出 10 个问题压垮用户
- 问题要具体，附带选项（如"是 A 还是 B？"），降低用户回答成本
- 如果某个决策有明显的行业惯例，可以提出推荐方案让用户确认，而不是完全开放式提问

---

### 第二步：判断模块类型，确定章节结构

根据用户描述，识别模块类型，动态选择章节组合：

#### 模块类型识别

| 模块特征关键词 | 识别为 |
|---|---|
| 增删改查、管理、列表、详情 | CRUD 管理类模块 |
| 登录、注册、鉴权、token、权限、角色 | 认证鉴权类模块 |
| 上传、下载、文件、图片、OSS | 文件存储类模块 |
| 通知、消息、邮件、短信、推送 | 消息通知类模块 |
| 统计、报表、图表、数据分析 | 数据统计类模块 |
| 搜索、检索、全文搜索、ES | 搜索类模块 |
| 定时任务、Job、调度、批处理 | 任务调度类模块 |
| 支付、订单、交易 | 交易类模块 |
| 以上特征混合或不明确 | 综合类模块（兜底） |

#### 章节选择规则

**所有模块都包含的基础章节：**
1. 概述（背景、目标、范围、术语）
2. 技术选型（根据模块特征推荐所需中间件，说明选型理由，不需要的不写）
3. 系统架构定位（当前模块在整体系统中的位置，依赖关系图）
4. 数据库设计（表结构、字段说明、索引设计）
5. 分层设计（DDD 四层：Infrastructure → Domain → Application → User Interface，各层职责与对象说明）
6. 核心接口设计（请求/响应结构，关键字段说明）
7. 核心业务流程（关键流程的文字描述或伪代码）
8. 异常处理设计
9. 测试要点
10. 实施顺序建议

**按模块类型追加的章节：**

- **CRUD 管理类**：追加「分页与筛选设计」、「逻辑删除与数据一致性」
- **认证鉴权类**：追加「Token 设计与生命周期」、「权限模型设计」、「安全边界说明」
- **文件存储类**：追加「存储策略设计」、「文件元数据管理」、「大文件/并发处理方案」
- **消息通知类**：追加「消息模板管理」、「发送策略与重试机制」、「幂等性设计」
- **数据统计类**：追加「数据来源与口径定义」、「缓存策略」、「数据一致性说明」
- **搜索类**：追加「索引设计」、「查询策略」、「与数据库的同步方案」
- **任务调度类**：追加「任务定义与触发规则」、「并发控制与幂等」、「失败重试与告警」
- **交易类**：追加「状态机设计」、「分布式一致性方案」、「对账与补偿机制」

---

### 第三步：逐章生成，遇到不确定立即提问

**生成节奏：**
- 按章节顺序生成，每完成 2-3 个章节输出一次，不要等全部写完再输出
- 遇到以下情况，**必须停下来提问，不能继续**：

**必须提问的触发条件：**

| 情况 | 示例提问 |
|---|---|
| 字段类型/长度不明确 | "create_time 用 DATETIME 还是 BIGINT 时间戳？" |
| 接口 URL 风格不确定 | "路由风格用 RESTful（/posts/{id}）还是动词式（/getPostById）？" |
| 分页方式不明确 | "分页用 offset 分页还是游标分页？" |
| 主键策略不确定 | "主键用数据库自增还是雪花 ID？" |
| 缓存策略不明确 | "这个接口需要缓存吗？如果需要，缓存时间大概多久？" |
| 权限粒度不清楚 | "这个接口是登录即可访问，还是需要特定角色权限？" |
| 业务规则有歧义 | "文章删除是逻辑删除还是物理删除？逻辑删除后是否还能恢复？" |
| 关联关系不明确 | "用户和文章是一对多，那删除用户时，文章怎么处理？" |
| 并发/幂等需求未提及 | "这个接口有并发提交的场景吗？是否需要幂等控制？" |

**提问格式规范：**
```
⚠️ 需要确认：

[问题描述，说明为什么需要这个信息]

选项：
A. xxx（适合 xxx 场景）
B. xxx（适合 xxx 场景）
C. 你有其他方案

确认后我继续生成「{当前章节名}」。
```

---

### 第四步：生成完整文档并输出文件

所有章节生成完毕后：

1. 将完整内容写入文件，路径：`/mnt/user-data/outputs/{模块名}_技术设计文档.md`
2. 调用 `present_files` 工具将文件提供给用户下载
3. 在对话中给出简短总结：包含哪些章节、有哪些值得关注的设计决策

## 文档写作规范

### 语言与格式
- 全程中文，技术术语保留英文原文（如 `Controller`、`DAO`、`LONGTEXT`）
- 表格用于字段说明、接口参数、索引说明
- 代码块用于 SQL 建表语句、Java 接口签名、请求/响应 JSON 示例
- 不使用模糊措辞（如"根据实际情况"、"视业务需要"），要给出明确的推荐方案

### 数据库设计规范（默认遵循，用户可覆盖）
- 主键默认推荐雪花 ID（BIGINT），对外用字符串形式避免 JS 精度问题
- 必含公共字段：`create_time`、`update_time`、`is_deleted`（逻辑删除）
- 字段注释必须填写
- 索引说明需注明类型（唯一索引/普通索引）和用途

### 接口设计规范（默认遵循，用户可覆盖）
- RESTful 风格
- 统一响应结构：`{ code, message, data }`
- 分页响应包含：`{ list, total, page, size }`
- ID 字段在 JSON 中序列化为字符串类型

### DDD 四层架构规范

项目采用**严格 DDD 四层架构**，各层职责和依赖方向不可违反：

```
┌─────────────────────────────────┐
│         User Interface 层        │  ← 接收请求，参数校验，响应封装
│  XxxController                  │
│  XxxReqDTO / XxxRespDTO         │
├─────────────────────────────────┤
│         Application 层           │  ← 用例编排，事务边界，防腐转换
│  XxxApplicationService          │
│  XxxAssembler（DTO ↔ Domain）   │
├─────────────────────────────────┤
│           Domain 层              │  ← 核心业务规则，不依赖任何框架
│  XxxDomain（聚合根/实体）        │
│  XxxDomainService（跨聚合逻辑） │
│  XxxRepository（接口，domain定义）│
│  XxxDomainEvent（领域事件）      │
├─────────────────────────────────┤
│        Infrastructure 层         │  ← 技术实现，依赖倒置
│  XxxRepositoryImpl              │
│  XxxMapper（MyBatis interface） │
│  XxxDAO（封装 Mapper）          │
│  XxxDO（数据库映射对象）        │
└─────────────────────────────────┘
```

**关键约束（文档设计必须遵守）：**
- Domain 层不得 import Spring 注解（`@Service`、`@Autowired` 等）
- Domain 层不得直接依赖 Infrastructure 层，只能依赖 Repository 接口
- Application 层持有事务（`@Transactional`），Domain 层不加事务注解
- Controller 层只能调用 ApplicationService，不能直接调用 DomainService
- DTO 转换统一由 Assembler 负责，不在 Controller 或 Domain 中做转换
- DO（数据库对象）只在 Infrastructure 层流转，不能透传到 Application 层以上

**命名规范：**
```
User Interface 层：
  XxxController
  XxxReqDTO / XxxCreateReqDTO / XxxUpdateReqDTO
  XxxRespDTO / XxxListItemRespDTO

Application 层：
  XxxApplicationService
  XxxAssembler

Domain 层：
  Xxx（聚合根，无后缀）/ XxxEntity（非聚合根实体）
  XxxDomainService
  XxxRepository（接口）
  XxxDomainEvent

Infrastructure 层：
  XxxRepositoryImpl
  XxxMapper
  XxxDAO
  XxxDO
```

## 质量检查清单

文档生成完毕前，自检以下项目：

- [ ] 所有表字段都有中文注释
- [ ] 所有接口都有请求/响应示例
- [ ] 核心业务流程有完整描述（不能只有接口，没有流程）
- [ ] 异常场景都有对应的错误码和处理说明
- [ ] 没有遗留"待确认"或"视情况而定"的模糊描述
- [ ] 索引设计合理（高频查询字段有索引，没有过度索引）
- [ ] 实施顺序建议合理（前置依赖排在前面）
- [ ] **技术选型检查：有缓存需求但未提及 Redis 的，补充缓存方案**
- [ ] **技术选型检查：有异步解耦场景但未提及 MQ 的，补充消息队列方案**
- [ ] **技术选型检查：有并发冲突风险但未提及锁的，补充分布式锁方案**
- [ ] **DDD 约束检查：事务边界标注在 ApplicationService 层**
- [ ] **DDD 约束检查：Repository 接口定义在 Domain 层，实现在 Infrastructure 层**
- [ ] **DDD 约束检查：DO 对象未透传到 Application 层以上**
- [ ] **DDD 约束检查：DTO 转换由 Assembler 负责，未散落在 Controller 或 Domain 中**

如果有任何检查项未通过，回头补全，或向用户提问补全信息，再输出文件。
